# Graviton 4 D=5/D=6 unpack fix — A/B verification

**Date:** 2026-04-27
**Host:** AWS c8g (Graviton 4, Neoverse-V2 NEON)
**Methodology:** 5 alternated paired-t A/B pairs, `PIVCO_BENCH_QUICK=1`,
incremental rebuild between source swaps.

## Background

`extras/bench_unpack_fl_layout.c` (run today) showed
`flat_d5_unpack` / `flat_d6_unpack` running at **1.3 GB/s** on
Graviton 4 vs **25 GB/s** on M4 — a 20× cliff with the same source.
The previous gate (`PIVCO_NEON_FAST_MULTI_TBL=0` on non-Apple) hid
this in production by routing D=5/D=6 through scalar fallback, but
the SIMD ceiling on G4 stayed unreachable.

## Root cause: stack round-trip in the byte load

Disassembling `current_d5_unpack` on G4 revealed:

```asm
ldr w5, [x1, w5, sxtw]  ; load 4 bytes -> int reg
ldrb w9, [x9, #4]       ; load 1 byte  -> int reg
str xzr, [sp, #8]       ; zero stack slot
str w5, [sp, #8]        ; int store -> stack
strb w9, [sp, #12]      ; int store -> stack
ldr d1, [sp, #8]        ; vector LOAD from stack  <-- store-forward stall
```

The compiler couldn't translate
`memcpy(&packed, bm_ptr, 5) + vsetq_lane_u64(packed, ...)` into an
elegant byte-wise vector load.  It went via int-regs + stack + vector
load.  On Neoverse-V2, **int-store -> vector-load forwarding does
not work cleanly**, causing a multi-cycle stall on every iteration.
M4 absorbs the same stall, which is why the older form looked fine
on M4.

For comparison, `flat_d3_unpack` (which uses byte-wise
`vsetq_lane_u8` instead of memcpy+vsetq_lane_u64) compiles to direct
`ldr b` / `ld1 {v.b}[k]` / `ins` — no stack involvement, no stall,
and runs at 7.7 GB/s on G4 (uint16x8-pattern's natural speed).

## Fix

Apply the same byte-wise pattern to D=5 and D=6:

```c
uint8x16_t bm_lo = vdupq_n_u8(0);
bm_lo = vsetq_lane_u8(bm_ptr[0], bm_lo, 0);
bm_lo = vsetq_lane_u8(bm_ptr[1], bm_lo, 1);
bm_lo = vsetq_lane_u8(bm_ptr[2], bm_lo, 2);
bm_lo = vsetq_lane_u8(bm_ptr[3], bm_lo, 3);
bm_lo = vsetq_lane_u8(bm_ptr[4], bm_lo, 4);
/* (one more for D=6) */
```

Microbench result (`extras/bench_unpack_fl_layout.c`):

| | M4 (before → after) | G4 (before → after) |
|---|---|---|
| D=5 | 25.6 → 30.0 GB/s (+17%) | 1.3 → 5.8 GB/s (**+345%**) |
| D=6 | 25.9 → 28.9 GB/s (+12%) | 1.3 → 5.2 GB/s (**+300%**) |

## Re-enabling the SIMD path: direct only, scatter still gated

With the unpack now ~5× faster, the SIMD path could plausibly beat
scalar in production.  Tested both gate states:

**Full gate-on** (D=5/D=6 SIMD in BOTH `flat_decode_direct_neon` and
`flat_decode_scatter_neon`): big wins on flat_M5/M6 (+60-64%) but
significant losses on bell_s30/s80, proba02, image_jpeg, chinese_text
(-3 to -7%).  The scatter-path TBL setup overhead dominates when the
path fires intermittently with smaller `n`.

**Direct-only enabled** (final patch): direct path D=5/D=6 always
SIMD; scatter path D=5/D=6 still gated to scalar via the existing
`PIVCO_NEON_FAST_MULTI_TBL` macro.  Reasoning: direct path runs with
n=8192 (the full pivco block), so the per-call TBL setup amortises
over enough work that even Neoverse-V2's slower vqtbl{2,4}q_u8 wins.
Scatter path runs with smaller n where the overhead matters.

## Cross-platform impact

- **Graviton 4**: flat_M5 +60%, flat_M6 +64%; bell_s30/s80/zipfian
  *unchanged* because scatter-path gate keeps them on scalar.
- **M4**: D=5/D=6 unpack microbench +12-17%, end-to-end no regression
  on key distributions; flat_M5/M6/M7 within run-to-run variance.
- **Xeon AVX-512 / Zen 3 SSE4.1**: file unchanged (NEON-only).
